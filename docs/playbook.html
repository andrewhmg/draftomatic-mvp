1. Language Selection

What we write in, and why.

We use Python 3.11, stdlib only (no Flask, no Django, no pip installs at runtime) for the entire product: server, content pipeline, topic generator, metrics, and test suite.

  • Zero runtime dependencies. A new machine only needs Python itself; git clone and python3 server.py boots the whole app. In a serverless deployment (Vercel) this keeps the footprint tiny.
  • It is the language our AI stack speaks natively. Our Ollama integration and content templating are pure Python; stdlib http.server routing, json, and unittest-style checks keep the surface auditable.
  • Generated HTML is rendered server-side from Python dicts (article = {intro, sections[], conclusion} keys), so there is no second client-side language to learn.
When we do need a second language it will be TypeScript for a future browser editor — until then, Python everywhere, stdlib everywhere.

2. IDE Selection & Setup

Get a working editor and a running app in under 30 minutes.
  1. Install VS Code (our standard editor, free): code.visualstudio.com/download. The uninstall-code command in our repo notes moves it to Applications on macOS.
  2. Install Python 3.11+: python.org/downloads — or verify with python3 --version. No other runtimes needed.
  3. Install Ollama (local LLM runtime that powers AI generation): ollama.com/download, then:
ollama pull glm-5.3-flash:cloud   # the model our pipeline calls
ollama list                       # verify it downloaded
  1. Clone and boot the app:
git clone https://github.com/andrewhmg/draftomatic-mvp.git
cd draftomatic-mvp
python3 server.py                 # serves http://127.0.0.1:8765
  1. Open the folder in VS Code and install these two extensions from the Extensions marketplace: Python (Microsoft, ms-python.python) and Ruff (astral, charliermarsh.ruff). Ruff in-editor is wired to the repo's ruff.toml, so you see the same lint verdicts the pre-commit gate enforces.
  2. Verify your setup: visit http://127.0.0.1:8765 — you should see the Draftomatic dashboard. If the AI generation step is slow, that's normal: topic planning takes ~20s, each article ~35s on the local model.
The app runs fine with Ollama stopped — a template engine takes over and writes placeholder-quality drafts, so you can develop UI/flow work offline.

3. Development Strategy

Kanban: our process and how a work item moves.

We run Kanban with a four-column board and WIP limits, exercised week by week during the MVP build. Card lifecycle:

Backlog → In Progress (WIP 2) → Review → Done
  • Backlog holds user-facing stories plus technical cards from the test suite (every failing or new check becomes a card with its test name in the title).
  • Pull, don't push: you take the top card only when your In-Progress column has room.
  • Definition of Done for every card: code on main, test_draftomatic.py passes with your change included, and the README covers any new endpoint.
  • Weekly planning meeting (Monday, 15 min): reorder Backlog against last week's metrics (/api/metrics funnel numbers) instead of by feel.

4. Git Strategy & Controls

Trunk-based with short-lived branches; review before merge.
  • Main is always shippable. Every push to main is auto-deployed to production by Vercel — never commit straight to main.
  • Branches: short-lived, named <area>-<change>, e.g. metrics-funnel-endpoint, llm-json-parity. Lifespan target: same day.
  • Commit messages: area: what changed — e.g. metrics: append-only event log + /api/metrics session aggregation. Present tense, no issue numbers needed.
  • Review control: open a GitHub pull request on andrewhmg/draftomatic-mvp; a second pair of eyes approves before merge, and the PR description must state which test checks cover the change.
  • Never in git: runtime state. data/state.json, data/articles/, published/, covers/, server.log, .env are all in .gitignore. Secrets live only in environment variables.
Why trunk-based instead of full git-flow: we are a two-pizza team shipping to one production app. Develop/release branches add ceremony without adding safety at our size; the PR review requirement is where our control actually lives.

5. Issue Tracking

Trello — where work lives.
  • Tool: GitHub Issues on our repo (label-based Kanban) — board lives at github.com/andrewhmg/draftomatic-mvp/issues. Why not Trello: labels backlog / in-progress / review / done mirror the section-3 columns and every card sits one click from the PR that does the work.
  • Card anatomy: title = user-visible behavior; body = acceptance criteria as a checklist; every card carries at least one test-suite check name so QA maps 1:1 to code. Area labels (llm, ui, metrics, deploy) tag the sprint.
  • Link cards to code: paste the issue number into the PR body (Fixes #N) — merging the PR auto-closes the card, which is our Done transition.
  • Day-one task: pick any backlog issue, run the setup in section 2, and fix the card end-to-end — it is the fastest way to learn our whole loop.

6. AI Agents & Controls

Our product IS an AI pipeline — these rules keep it honest.

Approved tools: Ollama running the glm-5.3-flash:cloud model locally (product generation + dev assistance), and Claude-class assistants for boilerplate and review. Unapproved: any cloud LLM with customer data.

The five guardrails (all tested in CI)

  • 1. Fenced-JSON parsing only. The model is instructed to return JSON; the integration accepts fenced ```json blocks and tolerates chatter preambles, and unit checks (llm: fenced JSON parses, llm: preamble tolerated, llm: garbage rejected) prove malformed output never reaches the app.
  • 2. Kill-switch env var. DRAFTO_DISABLE_LLM=1 forces template mode for any run — demonstrated in tests; it is also how the test suite runs fully offline.
  • 3. Tag every AI artifact. Generated drafts carry a visible generator: "AI ..." pill in the UI. A reader can always tell machine-written from human-edited.
  • 4. Length gates. Regeneration must stay in the 600–1000 word band (regenerated body in band check) — no runaway generations.
  • 5. Human review before publish. Nothing a model wrote goes live without a person pressing Publish in the dashboard (or the autopilot window a human explicitly enabled and can pause — pause/resume are tested endpoints).
Confidentiality rule: never paste customer site data, credentials, or unpublished business content into an AI tool other than our local Ollama runtime.

7. Code Quality

Ruff lint gate — configured in the repo, enforced before every commit.
  • Linter: ruff with the repo's ruff.toml — rule sets E (pycodestyle errors), F (pyflakes), W (warnings); line-length = 120; target-version = "py311"; E501 (long lines) ignored for HTML/SVG template literals.
  • Enforcement: a pre-commit hook (`.git/hooks/pre-commit`, installed with the clone via scripts/install-hooks.sh) runs ruff check . and blocks the commit on any finding. Fix with ruff check . --fix.
  • Formatting: ruff's formatter profile, 120 cols — same tool does lint and format, so one config, one gate.
  • Vulnerability scanning: stdlib-only means no third-party runtime deps to audit; dependencies are dev-only (ruff) and checked with python3 -m pip install ruff && ruff check . fresh each release. The attack surface we guard instead is input handling: publish keys are validated and a bad key is a tested failure path, not a crash.

8. Testing Frameworks

One self-contained suite: test_draftomatic.py — stdlib only.
  • What it does: boots the real server on a scratch port, copies the data state aside and restores it afterward, then drives the full API flow: health, pages, connect, topics, generate, regenerate, publish, retry, autopilot.
  • 54 checks (verified passing Oct 10, 2026) across compile checks, LLM plumbing unit tests, metrics plumbing, and every HTTP endpoint including failure paths (publish with a bad key must fail with a logged attempt number, not corrupt state).
  • How testing fits the workflow: python3 test_draftomatic.py before pushing — its exit code is the merge gate, and every Trello card carries the test names that cover it (see section 4).
  • Run verbose to see every check: python3 test_draftomatic.py -v
If your change touches store.py, server.py, or metrics.py, add a named check to the suite in the same PR. A feature without a test name on its card is not Done (section 3).

9. Other Controls, Tools & Procedures

Deployment, secrets, demo uptime, and where things live.

Deployments

  • Local dev: python3 server.py → http://127.0.0.1:8765.
  • Production: Vercel, free tier, auto-deploy from main: draftomatic.vercel.app. Deploy config lives in vercel.json; scripts/finalize_deploy.py bakes the metrics snapshot at build time. Template mode serves on Vercel (serverless cannot reach the laptop's Ollama) by design.
  • Rollback: vercel rollback in the project, or revert the offending commit on main — Vercel redeploys the prior build automatically.

Secrets & on-call

  • Secrets handling: no secrets in code, ever. Framer publish API keys and any future tokens live in environment variables; the publish key check failing on a bad key is a tested path (publish with bad key -> failed). The team password vault is 1Password; ask Andrew for invites on day one.
  • On-call: currently Andrew. If production is down (draftomatic.vercel.app erroring), check vercel logs first, then Vercel status; if the local demo server is down, restart with launchctl kickstart -k gui/$(id -u) com.draftomatic.server and verify with curl -s localhost:8765/api/health.
  • Demo data resets are a deploy risk: never hand-edit files under data/ — always through the API so the state file and metrics stay consistent.
  • Repo map: server.py (HTTP + endpoints) · store.py (state) · content.py (template engine) · llm.py (Ollama client) · topics_gen.py · metrics.py (event log + funnel aggregation) · test_draftomatic.py · scripts/.
